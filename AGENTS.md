# Правила разработки «СЖ Саратов»

## Перед изменением
- Прочитайте README.md, docs/requirements.md и код затрагиваемой области.
- Стек: Python 3.12+, FastAPI, asyncio, SQLAlchemy 2, Pydantic 2; React, TypeScript, Ant Design, SCSS; Docker Compose. Не заменяйте стек без решения владельца.
- Работайте небольшими согласованными изменениями. Не перезаписывайте чужую работу и не делайте несвязанные рефакторинги.

## Архитектура и данные
- Имена функций и методов пишите без начального подчёркивания, например `release_slots`. Сохраняйте стандартные специальные методы Python, например `__init__`.
- Backend: domain — независимые бизнес-правила; application — сценарии и порты; infrastructure — SQLAlchemy и внешние сервисы; api — HTTP и валидация. Зависимости направлены внутрь.
- Держите DTO в `application/models`, Pydantic-схемы в `api/schemas`, ORM-модели в `infrastructure/models`. Доменные модели с бизнес-правилами размещайте в `domain` по предметной области.
- Преобразования ORM-моделей в доменные объекты и записи выносите в `infrastructure/mappers`. Называйте функции по тому, что они преобразуют.
- Общие чистые утилиты выносите в `app/utils` по назначению. Константы и наборы значений храните отдельно от сценариев, рядом с нужной областью или в `app/constants`, если ими пользуются несколько слоёв.
- Пользовательские исключения объявляйте в `exceptions.py` соответствующего слоя. Преобразование ошибок в HTTP-ответы держите в `api/exceptions.py`.
- Не помещайте SQL, HTTP или зависимости FastAPI в domain/application. Не выполняйте блокирующий ввод-вывод в async-обработчиках.
- Схему базы изменяйте только через Alembic. Сохраняйте совместимость API и существующих данных; явно документируйте несовместимые изменения.
- Права проверяйте на сервере для каждого объекта. Скрытая кнопка не является защитой. Пользователь может состоять в нескольких отделениях и совмещать роли.
- Плановая неделя: среда–вторник, часовой пояс Europe/Saratov. Суббота и понедельник — выходные для напоминаний.
- Не выдавайте предположения за требования. Вносите нерешённые вопросы в docs/requirements.md.

## Качество
- Пишите тесты по AAA (Arrange → Act → Assert): подготовьте данные, выполните действие, проверьте результат. Отделяйте этапы пустыми строками. Не добавляйте формальные комментарии `# Arrange`, `# Act`, `# Assert` и их аналоги на frontend. Параметры и фикстуры могут выполнять роль Arrange. В последовательном интеграционном сценарии выделяйте этапы каждого проверяемого шага.
- Для новой бизнес-логики и исправлений ошибок добавляйте содержательные тесты, включая отказ в доступе и граничные случаи.
- Backend: `python -m pytest`, `python -m ruff check .`, `python -m ruff format --check .`, `python -m mypy app` из backend.
- Frontend: `npm run lint`, `npm run typecheck`, `npm test`, `npm run build` из frontend.
- Перед завершением выполните все относящиеся к изменению проверки. Сообщите фактические результаты и ограничения; не утверждайте, что непроверенное работает.
- Русский интерфейс, доступные подписи, состояния загрузки/ошибки/пустых данных, работоспособность на телефоне обязательны. Используйте общие компоненты и тему.
- Согласовывайте типы frontend с OpenAPI. Не подменяйте ошибки сервера демонстрационными данными.

## Безопасность и совместная работа
- Не коммитьте секреты, базы, вложения, реальные контакты и персональные данные. Демонстрационные имена и данные — только синтетические.
- Демо-вход допустим исключительно в явно включённом локальном режиме. Не подключайте его к опубликованному приложению.
- Не запускайте миграции, рассылки, публикацию или разрушительные операции против чужой среды без соответствующего поручения.
- Обновляйте документацию запуска и .env.example вместе с настройками. Фиксируйте зависимости lock-файлами.

## Новые модули платформы
- Сохраняйте CSRF, HttpOnly-сессии, ограничения OTP и проверку scope. Не добавляйте обход через demo-заголовок при настоящей сессии.
- Production запрещает локальные коды и demo. Проверяйте доступ к скачиванию файлов, приватность молитв и уведомлений.
- Для бронирований и ёмкости слотов нужны конкурентные проверки; фоновые задания должны быть идемпотентными.
- Время храните в UTC, календарный недельный цикл вычисляйте в Europe/Saratov. Не отправляйте напоминания в субботу и понедельник.
- Меняйте миграции вместе с моделями, проверяйте обновление/откат и alembic check. Не редактируйте применённые 0001/0002.
- Не заявляйте проверку SMTP/push/PostgreSQL без фактического прогона. Бизнес-правила см. docs/decisions.md и docs/access-matrix.md.
